# 🗺️ Стратегический роадмап внедрения Data Mesh

Данный документ описывает пошаговый план трансформации управления данными компании «Будущее 2.0» на горизонте **18 месяцев** — от централизованного монолитного DWH к децентрализованной модели **Data Mesh**. Каждый этап привязан к конкретным бизнес-целям и измеряемым KPI.

---

## 🎯 Бизнес-цели трансформации

Прежде чем переходить к этапам, зафиксируем, **зачем** мы это делаем:

| № | Бизнес-цель | Измеримый результат |
| :--- | :--- | :--- |
| 1 | **Сократить Time-to-Insight** — время от появления данных до бизнес-решения | С 2 недель → до 2 дней |
| 2 | **Повысить качество данных** за счёт ответственности владельцев доменов | Снижение инцидентов на 80% |
| 3 | **Снизить нагрузку на центральную IT-команду** | 70% отчётов — self-service |
| 4 | **Сократить TCO** инфраструктуры и аналитики | -30% к затратам на 3-й год (см. [tco-analysis.md](tco-analysis.md)) |
| 5 | **Обеспечить масштабируемость** при запуске новых бизнес-направлений | Новый домен подключается за 4-6 недель |

---

## 👥 Ключевые роли в Data Mesh

Успех Data Mesh зависит не от технологий, а от **людей и процессов**. Ниже — целевые роли и их ответственность.

| Роль | Зона ответственности | KPI | Аналог в классической модели |
| :--- | :--- | :--- | :--- |
| **Data Product Owner (DPO)** | Владелец Data Product в домене (например, «Пациенты»). Отвечает за бизнес-ценность, SLA, качество и доступность данных. | NPS потребителей данных, соблюдение SLA, количество активных потребителей | Product Owner / Business Analyst |
| **Domain Data Engineer** | Инженер внутри домена. Разрабатывает пайплайны, публикует события в Yandex MQ, формирует витрины данных. | Время доставки данных,覆盖率 тестов качества, uptime пайплайна | ETL-разработчик (центральный) |
| **BI-аналитик (Consumer)** | Потребитель Data Products. Строит дашборды в Yandex DataLens без участия IT. | Количество self-service отчётов, время создания отчёта | BI-разработчик (очередь в IT) |
| **Data Platform Team** | Центральная команда. Предоставляет самообслуживаемую платформу: Yandex Cloud, MQ, Data Catalog, мониторинг, стандарты. | Uptime платформы, время онбординга нового домена, удовлетворённость DPO | DBA / Администратор DWH |
| **Data Governance Lead** | Владелец политик: стандарты именования, метаданные, безопасность, compliance (152-ФЗ). | Соответствие регуляторным требованиям, полнота метаданных | CDO / Data Steward |

### 🟢 Фаза 1: Foundation & Pilot (Месяцы 1-3)

**Цель:** Доказать жизнеспособность модели Data Mesh на одном домене и получить быстрый бизнес-результат.

| Активность | Ответственный | Артефакт |
| :--- | :--- | :--- |
| Сформировать Data Platform Team (2-3 инженера) | CTO / VP Engineering | Устав команды |
| Определить стандарты Data Product: контракт, SLA, метаданные | Data Governance Lead | Data Product Specification v1.0 |
| Развернуть инфраструктуру: Yandex MQ, Data Catalog, DataLens | Data Platform Team | Terraform-модули (см. Task 1-2) |
| **Пилот:** Домен «Пациенты» публикует первый Data Product — «Регистрации пациентов» | DPO (Patients) + Domain Data Engineer | Data Product в каталоге |
| Обучить 5-10 BI-аналитиков работе с DataLens | Data Platform Team | Программа обучения |

**Бизнес-результат фазы:**
- Автоматический отчёт по регистрациям пациентов, который раньше готовился 3 дня, теперь обновляется в реальном времени.
- **Quick win** для получения финансирования следующих фаз.

**KPI фазы:**
- 1 опубликованный Data Product
- 5 активных BI-потребителей
- SLA Data Product ≥ 99%

---

### 🟡 Фаза 2: Expansion (Месяцы 4-9)

**Цель:** Подключить ключевые операционные домены и запустить Self-service BI.

| Активность | Ответственный | Артефакт |
| :--- | :--- | :--- |
| Подключить домены «Договоры» и «Биллинг» | DPO (Contract, Billing) | 2 новых Data Product |
| Настроить федеративный Data Catalog (единый поиск по всем доменам) | Data Platform Team | Yandex Data Catalog |
| Внедрить **Self-service BI** для финансовых метрик | BI-аналитики + DPO | Дашборды в DataLens |
| Настроить мониторинг качества данных (Great Expectations / dbt tests) | Domain Data Engineers | Тесты качества в CI/CD |
| Провести внутренний хакатон по использованию Data Products | Data Governance Lead | 3-5 новых use-cases |

**Бизнес-результат фазы:**
- Финансовые отчёты готовятся за **1 час** вместо 3 дней.
- Аналитики самостоятельно строят 40% отчётов без участия IT.

**KPI фазы:**
- 5+ опубликованных Data Products
- 40% self-service отчётов
- Снижение очереди задач в IT на 30%

---

### 🔵 Фаза 3: Scaling & AI (Месяцы 10-14)

**Цель:** Подключить аналитические и AI-домены, масштабировать Self-service BI на всю компанию.

| Активность | Ответственный | Артефакт |
| :--- | :--- | :--- |
| Подключить домен «Исследования» (AI/ML) | DPO (Research) | Data Product «Результаты ИИ-исследований» |
| Публикация ML-моделей как Data Products (Model-as-a-Service) | Data Scientists + Domain Data Engineer | API моделей в каталоге |
| Масштабирование Self-service BI на все отделы (продажи, маркетинг, HR) | BI-аналитики | 20+ дашбордов в DataLens |
| Внедрить Data Contracts между доменами (версионирование схем) | Data Governance Lead | Schema Registry |
| Запустить внутреннее сообщество Data Mesh Champions | DPO всех доменов | Ежеквартальные митапы |

**Бизнес-результат фазы:**
- Персонализация услуг на основе real-time данных → **+25% к конверсии cross-sell**.
- ML-модели доступны другим доменам как сервис.

**KPI фазы:**
- 10+ Data Products
- 70% self-service отчётов
- 3+ ML-модели, используемые другими доменами

---

### 🔴 Фаза 4: Optimization & Legacy Sunset (Месяцы 15-18)

**Цель:** Полностью отказаться от Legacy DWH и Apache Camel для аналитики, выйти на целевые показатели TCO.

| Активность | Ответственный | Артефакт |
| :--- | :--- | :--- |
| Миграция последних аналитических нагрузок с Legacy DWH | Domain Data Engineers | План миграции |
| **Отключение** старого ETL и Apache Camel для аналитики | Data Platform Team | Акт вывода из эксплуатации |
| Внедрить **FinOps** для оптимизации затрат на облако | Data Platform Team + DPO | FinOps Dashboard |
| Провести аудит соответствия 152-ФЗ в новой архитектуре | Data Governance Lead | Отчёт для compliance |
| Зафиксировать best practices и обновить стандарты | Все роли | Data Mesh Playbook v2.0 |

**Бизнес-результат фазы:**
- Достижение целевых показателей TCO (**экономия 30%** к инфраструктурным затратам).
- Полное соответствие регуляторным требованиям.

**KPI фазы:**
- Legacy DWH отключён на 100%
- TCO снижен на 30% (см. [tco-analysis.md](tco-analysis.md))
- 100% соответствие 152-ФЗ

## ⚠️ Риски роадмапа и митигация

| Риск | Вероятность | Влияние | Митигация |
| :--- | :---: | :---: | :--- |
| **Сопротивление доменов** («мы не хотим быть владельцами данных») | Высокая | Высокое | Обучение, назначение DPO с полномочиями, KPI в премии |
| **Нехватка компетенций** (Data Engineering, DataLens) | Высокая | Среднее | Внешние консультанты на фазу 1, внутреннее CoE, хакатоны |
| **Разрастание затрат на платформу** | Средняя | Высокое | FinOps с 1-го дня, алерты на бюджет, автоскейлинг |
| **Падение качества данных при децентрализации** | Средняя | Высокое | Data Contracts, автоматические тесты, SLA в каталоге |
| **Задержка миграции с Legacy** | Средняя | Среднее | Strangler Fig, параллельная работа не более 6 месяцев на домен |
